3 · TLS ClientHello 抓取与回显

✅ 结论先行：完全可行，且与项目「安全攻防 / 调试留痕」的定位高度契合，建议作为下一迭代的核心功能。

3.1 为什么值得做

ClientHello 是 TLS 握手中客户端发送的第一条明文消息（加密发生在之后），包含客户端指纹、SNI、密码套件、扩展列表等关键情报，天然适合 MITM 留痕场景：

  • 客户端识别：基于 ClientHello 计算 JA3 / JA4 指纹，区分 OpenAI SDK、curl、python requests、浏览器、攻击工具，回答「是谁在调用本服务器」；
  • 外带检测：安全攻防中提示词/敏感数据可能被编码进 SNI（类似 DNSlog 外带），抓取 ClientHello 即抓到这条隐蔽通道；
  • 握手留痕：补全「连接级」视角 —— 当前只记录应用层 HTTP，链路层/会话层完全黑盒；
  • 回显展示：抓到的字段（版本、SNI、密码套件、ALPN、JA3/JA4、原始 hex）结构化落到请求详情页，一条对话一个 TLS 面板。

3.2 抓取原理

TLS 握手首条消息格式固定，可在 TCP 层直接解析：

TCP stream ──► TLS Record Header(5B: type=0x16 handshake, version, length)
              ──► Handshake Header(4B: type=0x01 client_hello, length)
              ──► ClientHello 明文体:
                    legacy_version(2) | random(32) | session_id |
                    cipher_suites(2B len) | compression_methods |
                    extensions(2B len) ─► SNI / ALPN / supported_groups /
                                          signature_algorithms / …

标准库 crypto/tls 的 GetConfigForClient 只能拿到结构化后的 ClientHelloInfo（SNI、CipherSuites、SupportedProtos…），拿不到原始字节，无法精确计算 JA3/JA4。因此正确做法是在 TLS 层之前 peek 原始字节：

sequenceDiagram
    participant C as 客户端
    participant L as ProbeListener(TCP层)
    participant T as tls.Server
    participant H as HTTP Handler
    C->>L: Accept() 建立连接
    L->>L: peek 前若干字节(不消费)
    L->>L: 判定 0x16 且类型 client_hello → 解析 + 算 JA3/JA4
    L-->>T: 回放 peek 的字节 + 剩余流, 正常进行 TLS 握手
    T-->>H: 解密后 HTTP 请求到达
    Note over L,H: 解析结果存入连接上下文(goroutine-local/context)
首个 HTTP 请求落地时写入 Request.Metadata["tls_client_hello"]

3.3 实现方案对比

方案抓取能力改动面评价
A · ProbeListener + 自研解析 原始字节、JA3/JA4、全部扩展字段 新增 pkg/tlsprobe；Server 监听层包一层 ★ 推荐 全量可控，无第三方依赖，约 300~500 行
B · 仅 GetConfigForClient 无原始字节，无法算精确 JA3/JA4 改动最小（tls.Config 回调） 回显信息残缺，不满足诉求
C · 引第三方库（utls / go-ja3） 完整 + 现成指纹 新增依赖 可行；自研解析 ClientHello 本身并不复杂，倾向 A

3.4 落地步骤（方案 A）

  1. 新包 pkg/tlsprobe：ParseClientHello(raw []byte) (*ClientHello, error) —— 解析版本/随机数/密码套件（含 IANA 名称映射）/扩展（SNI、ALPN、supported groups、signature algorithms）/计算 JA3 与 JA4；同时提供 ProbeListener（包装 net.Listener，Accept 时 peek + 解析 + 回放）。
  2. Server 支持 TLS 监听：ServerConfig 增加 TLSCertFile / TLSKeyFile / AutoTLS；Run() 改为 tls.Listen；开发落地自动生成自签证书（写盘缓存），生产可用用户提供证书。
  3. 数据落库：握手解析结果序列化进 Request.Metadata["tls_client_hello"]，随请求记录一并保存/查询 —— 无需新增数据库字段；同时补一张可选的独立「握手事件」视图用于无 HTTP 请求的连接。
  4. UI 回显：详情页新增 TLS 握手 标签页，展示字段名/值对照表 + JA3/JA4 指纹徽章 + 原始 hex（details/summary 折叠），暗色主题下同步适配。
  5. 配置与文档：新增 --tls、--tls-cert、--tls-key、--auto-tls 启动参数；更新 README 与指南页（补 HTTPS base_url 接入示例 https://host:port/v1）。
  6. 测试：单元测试覆盖 ClientHello 解析（含真实 Chrome/curl/Go 握手样本）、JA3/JA4 已知指纹向量；集成测试验证「HTTPS 请求 → 详情页出现 TLS 面板」。

3.5 需要留意的点

  • 证书信任：自签证书下客户端需跳过校验（verify=False）或导入 CA —— 需在 UI/README 明确引导；
  • TLS 与明文共存：建议同一端口做协议探测（peek 后判定 0x16→TLS、否则 →HTTP），不影响现有 HTTP 用法；
  • minVersion 策略：解析器需兼容 TLS 1.2/1.3 及 supported_versions 扩展中的协商降级；
  • 敏感字段：random、session_id 等二进制需 hex 编码展示，避免破坏 JSON/前端渲染。
